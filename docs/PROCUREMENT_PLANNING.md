# 采购方案分析与确认

## 业务闭环

采购方案位于“可研报告”和“招标文件生成”之间：锁定可研版本 → 全文分块解析 → 建设内容、采购包、预算和明确采购安排提取 → 规则与证据复核 → 推荐及备选方案 → 用户调整并确认 → 每份独立匹配模板 → 单份或批量生成招标文件 → 按选定采购包生成合同草稿。

历史成品不补造方案或证据。未绑定采购方案的原有招标生成，以及上传外部招标文件直接生成合同的入口保持不变。

## 数量与范围口径

“招标文件份数”只统计当前方案中采购方式为招标且状态有效的独立主文件组。一份主文件关联三个采购包仍为 1 份；DOCX/PDF、附件和历史版本均不增加份数。非招标方式单独统计，当前未支持生成时只提示，不伪装为可生成。

`recommended_document_count` 可以为 null。影响范围或份数的来源冲突、解析缺口、未知建设范围、遗漏内容或未归属采购包存在时返回 null，而不是 0。只有完整范围均被确认排除、已采购、远期或采用其他方式时才能返回 0。

## 证据与预算

证据保存来源版本和 SHA-256、章节、真实页码或段落/表格定位、原文片段、提取值、规范化值、证据类型和状态。DOCX 不伪造页码；扫描件和失败页进入 P0 待确认。上传内容仅作为不可信业务数据，提示词或代码不能改变系统规则和权限。

金额使用数据库 Numeric 和 Python Decimal。项目总投资、投资明细、采购包估算、已确认采购预算、最高投标限价和合同成交价互不等同。只有总投资时各采购包预算与限价保持空值；预算分配关系检查重复、分摊合计和超额分配。

## 规则引擎（feasibility-procurement-v1）

可研采购划分采用「抽取 + 规则裁决」：

1. **混合抽取**：材料含 `独立主招标文件` / `采购包` 等显式标注时，走确定性解析（不调大模型）；否则才调用 LLM，且结果仅为候选。
2. **内置核心规则**：平台内置约 10 条可执行规则（缺划分阻断、范围未知、来源冲突、未完整解析、禁止总投资复制到采购包、非招标排除计数、LLM 候选提示等）。
3. **可配置规则集**：`ProcurementRuleSet.rules_json` 若声明 `"version": "feasibility-procurement-v1"`，将在 `recalculate_plan` 中与内置规则一并执行；旧版仅描述性 JSON 仍只做适用性追溯。

规则输出进入 `ProcurementIssue.category=rule_engine`，P0 阻断份数与确认，P1/P2 用于确认与提示。

## 页面操作

进入项目 → 招标文件（顶部 5 步：来源选择 → 文件材料 → 字段确认 → 文档生成 → 文档确认）：

1. 在“来源选择 / 文件材料”上传采购依据材料，点击一次“上传并解析”。
2. 系统依次完成校验、解析、字段候选提取、采购方案分析，并生成待编制文件清单；不再单独进入“采购方案分析与确认”步骤页。
3. 解析成功后提示“已识别本项目需要编制 N 份文件”，随后进入“字段确认”。
4. 在字段确认页顶部用“待编制文件”下拉切换各主文件，分别核对并人工确认关键字段；切换时不丢失已填/已确认数据。
5. 全部待编制文件的关键字段确认完成后，才允许进入“文档生成”；存在缺失、冲突、格式错误或 AI 候选未确认时阻断。
6. 重新上传并再次解析时，会重新判断待编制清单；若可能影响已有字段确认，须用户确认，不得静默覆盖。
7. 招标文件定稿后进入合同阶段；绑定招标定稿，选择其一个或多个采购包生成对应合同草稿。合同价、供应商和履行日期不得从预算推断。

长文档分析按正文分块保存检查点，页面展示已完成分块和正文块数量。模型超时或任务被重新接管时，`POST /api/v1/procurement-analyses/{run_id}/retry` 会沿用同一分析记录并复用输入哈希一致的成功分块；工作进程中的看门任务按 `PROCUREMENT_ANALYSIS_RECOVERY_INTERVAL_SECONDS` 周期检查，并自动重新接管超过 `PROCUREMENT_ANALYSIS_STALE_AFTER_SECONDS` 未更新的排队、运行或重试任务。任务专用软/硬时限由 `PROCUREMENT_ANALYSIS_SOFT_TIME_LIMIT_SECONDS` 和 `PROCUREMENT_ANALYSIS_TIME_LIMIT_SECONDS` 配置。

## 脱敏演示结果

专项测试材料明确三项独立安排，程序结果为 3 份主招标文件和 3 个采购包：

| 主文件 | 采购包 | 采购范围 | 划分理由 | 来源证据 |
|---|---|---|---|---|
| 网络设备采购招标文件 | P1 网络设备包 | 交换机及网络配套 | 网络可独立验收 | DOCX 标题“可行性研究报告”下对应主文件与采购包段落 |
| 应用软件建设招标文件 | P2 应用软件包 | 应用软件开发与集成 | 软件成果独立验收 | DOCX 对应主文件与采购包段落 |
| 第三方测评服务招标文件 | P3 测评服务包 | 等保测评与软件测评 | 来源明确独立性要求 | DOCX 对应主文件与采购包段落 |

这些 DOCX 证据使用结构化段落定位，不显示伪造页码。测试材料未提供经批准预算、最高限价、正式规则适用结论和客户模板审批，因此它们保持待确认；这不改变来源已明确的 3 份文件结论，但会阻断正式定稿。

## 功能开关与回滚

`PROCUREMENT_PLANNING_ENABLED=true` 开启新分析入口；关闭后不允许新建分析，页面说明功能关闭，已有方案、文件和校验绑定不删除，也不能借此绕过已进入新流程文件的门禁。

升级使用 `alembic upgrade head`。迁移 `20260908_0009` 添加采购方案表和 generation_jobs/documents 的可空关联，`20260908_0010` 增加招标模板适用性确认，`20260908_0011` 将导出任务锁定到准确的可编辑文档 revision，`20260908_0012` 仅新增采购分析分块检查点表。优先采用关闭 `PROCUREMENT_PLANNING_ENABLED` 的应用级回滚；这会停止新分析但保留新数据及既有方案门禁。若只回退本次续跑机制，可降级到 `20260908_0011`，只删除检查点表，不影响分析记录和既有方案。若必须继续数据库回滚，应先停止新分析和生成任务、备份数据库，再依次降级；降到 `20260907_0008` 会删除采购方案新增数据，但不会删除迁移前项目、上传文件、历史文档和导出数据。生产回滚必须经过数据备份和审批，不由应用自动执行。
